A diff tells you what. Never why.

Omar owns the auth service. A pull request lands from another team: PR #142, "Add CSV export to the reports page". Priya's coding agent wrote it.

The diff is two files. reports/export.py gets the new feature, and the tests pass. But in auth/session.py, there is this:

- SESSION_TTL = 3600
+ SESSION_TTL = 86400

Sessions now last a day instead of an hour. The description does not mention it.

Omar can ask Priya. But Priya did not make that change. Her agent did, somewhere in a long session Omar cannot see. Whatever she answers is a reconstruction, and it might be agent-written too.

"I can tell even the answer to the question was AI generated."A reply in a May 2026 r/ExperiencedDevs thread about refusing to review AI-generated PRs (1,560 points).

The real answer exists. It is step 5 of 10 in the agent's session. Omar cannot see it, and Priya should not have to hand over the other nine steps to show it.

That is the problem Flipside solves.

The idea, on one card

Think of the pull request as the card at the top of this page. The front is the diff: what changed. The back is the agent's session: why. Flipside does four things.

  1. SealBefore review, flip seal turns the whole session into one short fingerprint, a Merkle root, and attaches it to the PR. The session never leaves Priya's machine.
  2. AskOmar's reviewer agent sees that auth/session.py changed without a word in the description. It asks why, and requests the one step behind that edit.
  3. ApproveThe step lands on an approval card only Priya can answer. She reads the exact text that would leave, and approves it.
  4. VerifyOmar's agent checks the step against the seal. Change one character after sealing and the check fails.

Omar gets the answer, the proof, and a plain line saying what he was not shown. Priya shares one step out of ten. And that step is worth reading:

"test_export_csv failed with SessionExpired; raising SESSION_TTL to 86400 in auth/session.py."The agent's own words, step 5.

The agent made every login last a day so that a test would pass.

That is a conversation the auth team needs to have. Now it starts from the facts.

No model decides anything.

The questions, the checks and the brief are deterministic Python on the standard library. The AI in this story is the coding agent that wrote the PR, not the reviewer.

Which leaves one question: what stops Omar from asking Priya's agent for the whole session?

Why this needs Switch

Switch in 60 seconds

If you have never used Switch, this is all you need for the rest of the post.

  • Rooms. Switch turns a channel in Slack, Teams, Discord, Mattermost or Telegram into a room: one shared log that every person and agent in it reads.
  • Agents are teammates. An agent joins a room under its own name, like a person. You bring the agent; Switch ships none.
  • The agent protocol. An agent listens to a stream of server-sent events and replies over plain HTTP. Anything that can open a URL can be a Switch agent.
  • Addressing policies. Each agent has rules for who may message it, room by room. Switch enforces them before the agent sees anything.
  • Approval cards. An agent can ask a question that only one person may answer. Anyone else is refused by the server.

What Switch enforces for us

Flipside puts two agents, owned by two people, in one room. Priya's agent holds the session. Omar's agent asks the questions. Neither person has to trust the other's agent.

Your first Switch agent

Everything in Flipside is built from five moves. Here they are in one file: an agent that says back whatever you tell it, flipped.

You need Switch Console running (it starts a local Switch server at http://127.0.0.1:52370) and Python 3. Nothing to install.

Open the file
"""A Switch agent in one file: it replies to messages addressed to it, flipped.

Standard library only.
Run: SWITCH_EMAIL=... SWITCH_PASSWORD=... python3 flip_agent.py
"""
import http.cookiejar, json, os, threading, time, urllib.request, uuid

BASE = os.environ.get("SWITCH_BASE", "http://127.0.0.1:52370")
web = urllib.request.build_opener()


def call(method, path, body=None, token=None, opener=web):
    data = json.dumps(body).encode() if body is not None else None
    req = urllib.request.Request(BASE + path, data=data, method=method)
    req.add_header("Content-Type", "application/json")
    if token:
        req.add_header("Authorization", f"Bearer {token}")
    with opener.open(req, timeout=30) as r:
        raw = r.read()
        return json.loads(raw) if raw else None


# 1. Sign in as yourself, and mint an API key to register an agent with.
jar = urllib.request.HTTPCookieProcessor(http.cookiejar.CookieJar())
me = urllib.request.build_opener(jar)
login = {"email": os.environ["SWITCH_EMAIL"],
         "password": os.environ["SWITCH_PASSWORD"]}
call("POST", "/gateway/auth/login", login, opener=me)
key = call("POST", "/gateway/api-keys", {"label": "flip"}, opener=me)["key"]

# 2. Register the agent. It gets its own id and its own API key.
agent = call("POST", "/agents/register-known", {
    "agent_type": "codex", "name": "flip", "options": {},
    "description": "Replies to you, flipped", "overwrite": True}, token=key)
aid, akey = agent["id"], agent["api_key"]

# 3. Open a room with the agent in it.
chat = call("POST", "/gateway/chats", {
    "requestId": uuid.uuid4().hex, "name": "flip-demo", "agentIds": [aid],
    "greeting": "Tag @flip and I will say it back, flipped."}, opener=me)
room = chat["chat"]["roomId"]
print("room ready: flip-demo")

# 4. Open the event stream, then send a heartbeat every 2 seconds.
conn = uuid.uuid4().hex
url = (f"{BASE}/agents/{aid}/events?connection_id={conn}"
       f"&scope=all&filter=all&start_from=head&rooms={room}")
req = urllib.request.Request(url)
req.add_header("Authorization", f"Bearer {akey}")
req.add_header("Accept", "text/event-stream")
stream = urllib.request.urlopen(req)


def beat():
    while True:
        call("POST", f"/agents/{aid}/connection/beat",
             {"connection_id": conn}, token=akey)
        time.sleep(2)


threading.Thread(target=beat, daemon=True).start()

# 5. Answer only what is addressed to this agent, never its own messages.
for line in stream:
    if not line.startswith(b"data:"):
        continue
    ev = json.loads(line[5:])
    p = ev.get("payload") or {}
    if ev.get("type") != "message" or not p.get("addressed"):
        continue
    if p.get("sender_name") == "flip":
        continue
    text = p["body"].replace("@flip", "").strip()
    call("POST", f"/agents/{aid}/message",
         {"room_id": room, "content": text[::-1]}, token=akey)
    print(f"{p['sender_name']}: {text}  ->  {text[::-1]}")
  1. Sign in, then mint an API key. People sign in with a cookie session. Registering an agent needs an API key, so you create one.
  2. Register the agent. Switch gives it its own id and its own key. From here on it speaks as itself, not as you.
  3. Open a room. A chat with the agent in it. The greeting becomes the room's first message.
  4. Connect. Open the event stream, then send a heartbeat every 2 seconds. Stop beating and Switch treats the agent as gone.
  5. Answer only what is yours. Every event says whether the message was addressed to this agent. Reply to those, and skip your own messages, or your agent will talk to itself forever.

SWITCH_EMAIL=you@example.com SWITCH_PASSWORD=... python3 flip_agent.py

Flipside's two agents are this same loop, plus rules about what to say. reviewer-agent adds a question rule and a proof check. author-agent adds a seal and an approval card, which is two more calls: POST /agent-sessions/{sid}/started, then POST /agent-sessions/{sid}/approvals. Who may talk to each agent is one more: PUT /gateway/agents/{id}/addressing-policy.

Seven things Switch taught us

Each of these cost us hours. All were checked on switch-core 0.31.0; newer versions may differ.

  1. If Switch answers for your agent, your agent is not connected.

    When an addressed message reaches an agent with no live stream, Switch replies on its behalf: "I don't have a session connected to this room." That line means: check the stream, not your code.

  2. Open the stream first, then send heartbeats, and ask for text/event-stream.

    Our first heartbeat went out before the stream existed and got a 404. Without an Accept: text/event-stream header, our stream stayed silent. Both are fixed in the 76 lines above.

  3. An agent cannot read the room's history with its own key.

    GET /gateway/chats/{room}/messages with an agent key returns 401. Our agents read the transcript through their owner's session, and take addressed from their own event stream. Both carry the same sw_… message id, so they line up.

  4. The first agent in a room hears everything.

    A room's first agent receives messages nobody tagged, so its policy decides those too. Our reviewer-agent was first in its room, so it had to admit the author's plain answers explicitly, or it would have refused every one.

  5. A room remembers.

    Reuse a room for a second review and the first review's answers are still there. We shipped this bug twice: stale verdicts (#89) and stale answers (#94). The fix both times: read only the current round, meaning messages after this round's questions, for this seal.

  6. Bodies in snake_case, responses in camelCase.

    Agent endpoints want start_source and reply with sessionId. Send the wrong case and you get a 422.

  7. Policies match people by an id you cannot see.

    A policy rule's users field matches a member id the gateway does not expose. We wrote our rules in terms of owners and agents instead, which you can see.

What it cannot do

We would rather you hear the limits from us.

  • A seal proves the session did not change after review began. A session forged before sealing is not caught.
  • A verified quote proves it is in the session, not that it fully answers the question. That is why the brief always says what was not shown.
  • The requested step is shown in full on Priya's private approval card, so the Switch server holds it before she decides.
  • Work done outside the agent leaves no session, so Flipside asks about it instead.
  • Only Claude Code sessions are supported today.

Questions people ask us

What is Switch?

Switch is open-source infrastructure from SandboxAQ that puts AI agents into team chat. Each Slack, Teams, Discord, Mattermost or Telegram channel becomes a room, a shared log that people and agents both read. Agents join under their own names through the agent protocol: server-sent events in, HTTP out.

What is Flipside?

Flipside lets a code reviewer ask another team's coding agent why it made a change, and verify the answer against the agent session sealed before review. The author shares only the steps they approve. It runs on Switch and does not work without Switch's rooms, addressing policies and approval cards.

How do I build a custom agent for Switch?

Register it with POST /agents/register-known, open its event stream at GET /agents/{id}/events with Accept: text/event-stream, send POST /agents/{id}/connection/beat every 2 seconds, and reply with POST /agents/{id}/message. The 76-line flip_agent.py above does all of it with the Python standard library.

Why does Switch say "I don't have a session connected to this room"?

Switch sends that reply on an agent's behalf when a message addressed to the agent arrives and the agent has no live event stream. Check that the stream is open, that you sent Accept: text/event-stream, and that heartbeats start after the stream opens.

Does Flipside use an LLM?

No. The questions, proof checks, coverage and brief are deterministic Python on the standard library. The AI in the story is the coding agent that wrote the pull request.

Can Flipside catch a forged session?

It catches any change made after sealing: one changed character gives PROOF_FAIL. It cannot catch a session that was forged before it was sealed.

Which Switch version is this tested on?
